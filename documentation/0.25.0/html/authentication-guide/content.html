About this guide

This guide covers configuring client authentication for Kroxylicious. It explains how the proxy authenticates Kafka clients using TLS and SASL, and how authentication information is turned into the authenticated subject that other filters can use.

Refer to the Kroxylicious Proxy guide for general proxy configuration and the Kroxylicious Operator for Kubernetes guide for deploying the proxy on Kubernetes.

This guide explains how to configure client authentication for the Kroxylicious proxy. It covers TLS and SASL authentication mechanisms, the different SASL authentication modes available, and how the proxy builds authenticated subjects from client identity information.

1. Overview of client authentication

Kroxylicious is a Layer 7 (application layer) proxy for the Kafka protocol. It understands and can act on the content of Kafka protocol messages, rather than simply forwarding TCP traffic.

This architecture has an important consequence for TLS: the proxy always terminates TLS connections from clients. Unlike a network-layer (Layer 4) proxy, it cannot pass TLS connections through transparently because it needs to read and potentially modify Kafka protocol messages. If TLS is configured between clients and the proxy, the proxy holds the server certificate and manages the TLS session with the client. A separate TLS session may be established between the proxy and the upstream Kafka brokers.

1.1. Authentication mechanisms

Client authentication in Kroxylicious can use either or both of the following mechanisms:

Client mutual TLS (mTLS)

The proxy requires clients to present a TLS client certificate during the TLS handshake. The proxy validates the certificate against a trust store containing trusted CA certificates. This provides strong client identity based on the certificate’s subject or subject alternative names (SANs).

SASL authentication

Kafka clients and brokers use the Simple Authentication and Security Layer (SASL) protocol to authenticate. The proxy can interact with this SASL exchange in several ways, ranging from transparently forwarding it to actively validating credentials. For more information about SASL authentication modes, see SASL authentication modes.

These mechanisms are not mutually exclusive. A deployment can use mTLS to establish transport-level identity and SASL to establish application-level identity.

1.2. The authenticated subject

When authentication succeeds, the proxy constructs an authenticated subject representing the client’s identity. A subject contains one or more principals — named identifiers such as a user name derived from a certificate DN or a SASL authorization ID.

Filters in the proxy chain can access the authenticated subject to make decisions about the client. For example, the authorization filter uses the subject to enforce access control policies, and the entity isolation filter uses it to provide per-client topic namespaces.

Without authentication, the subject is anonymous and identity-aware filters cannot function.

2. SASL authentication modes

The proxy can interact with the SASL authentication exchange between a Kafka client and broker in several ways. Each mode offers a different trade-off between simplicity, visibility, and security.

2.1. SASL Passthrough

In SASL Passthrough mode, the proxy forwards SaslHandshake and SaslAuthenticate requests from the client to the broker and relays the broker’s responses back to the client without inspecting or modifying them.

This is the default behavior when no SASL-related filter is configured. The proxy acts as a transparent intermediary for the SASL exchange.

In this mode, the proxy does not know the client’s identity. The authenticated subject remains anonymous, so identity-aware filters such as authorization or entity isolation cannot function.

2.2. SASL Passthrough Inspection

In SASL Passthrough Inspection mode, the proxy observes the SASL exchange as it passes through. It extracts the client’s authorization ID from the SASL messages without modifying them. The broker still makes the final decision about whether authentication succeeds or fails.

This mode is implemented by the SaslInspection filter. When the broker accepts the client’s credentials, the filter constructs an authenticated subject from the authorization ID, making the client’s identity available to other filters in the chain.

Mechanisms that transmit credentials in plain text (such as PLAIN) are disabled by default to avoid plain-text passwords existing in the proxy’s memory.

For the OAUTHBEARER mechanism, only JWT tokens that use signatures (JWS) are supported. JWT tokens that use encryption (JWE) are not supported. Unsigned JWT tokens are supported but not recommended for production use.

2.3. OAuthBearer Validation

OAuthBearer Validation is a specialized mode in which the proxy validates a client’s JWT bearer token before forwarding the SASL exchange to the broker. If the token is invalid, the proxy short-circuits the exchange and returns an error to the client without contacting the broker.

This mode is implemented by the OauthBearerValidation filter. It reduces load on the broker by rejecting clients with invalid or expired tokens at the proxy before their application requests are forwarded.

The filter validates tokens against a JSON Web Key Set (JWKS) retrieved from a configurable endpoint. It supports configurable token validation including expected audience, expected issuer, and custom claim names.

To limit the impact of repeated authentication failures, the filter applies exponential backoff to clients that present invalid tokens.

2.4. SASL Termination

In SASL Termination mode, the proxy handles the SASL authentication exchange itself, without forwarding SaslAuthenticate requests to the broker. The proxy validates the client’s credentials directly and constructs an authenticated subject on success.

This mode is implemented by the SaslTermination filter. It fully decouples client authentication from broker authentication, which can be useful when the proxy and broker use different credential stores or when you want to ensure that only authenticated clients' application requests are forwarded to the broker.

The SaslTermination filter supports the OAUTHBEARER, SCRAM-SHA-256, and SCRAM-SHA-512 SASL mechanisms. If a client attempts to use a mechanism that is not configured, the proxy rejects the handshake with an unsupported mechanism error and closes the connection. For OAUTHBEARER, the filter validates JWT tokens against a JSON Web Key Set (JWKS) retrieved from a configurable endpoint, checking the token signature, audience, issuer, and expiry. For SCRAM-SHA-256 and SCRAM-SHA-512, the filter validates client credentials against a pluggable credential store that provides the SCRAM derived keys for each user.

The filter supports session expiry and reauthentication (KIP-368). When a token’s expiry is reached, the client must reauthenticate or the connection is closed.

Because SASL is terminated at the proxy, certain Kafka APIs that depend on a broker-side SASL session are not available. The filter removes the Delegation Token APIs (CreateDelegationToken, RenewDelegationToken, ExpireDelegationToken, DescribeDelegationToken) and the SCRAM credential APIs (AlterUserScramCredentials, DescribeUserScramCredentials) from the ApiVersions response and rejects any requests for these APIs.

To mitigate timing side-channel attacks (such as username enumeration), the filter applies a configurable fixed delay to each authentication round. This ensures that authentication responses take a consistent amount of time regardless of the reason for success or failure.

3. Choosing an authentication approach

This section provides guidance to help you choose the right authentication approach based on your existing infrastructure, security requirements, and required proxy features.

3.1. Mutual TLS (mTLS)

Use mTLS when:

  • Clients can use certificates signed by a trusted issuer. While straightforward if you operate your own PKI, this approach also works with externally issued certificates if you trust the issuing CAs.

  • You want strong transport-level identity without depending on SASL.

  • You are willing to manage the operational overhead of certificate distribution, renewal, and revocation.

mTLS is independent of any SASL mechanism. The client’s identity is derived from the TLS client certificate, so even clients that do not use SASL authentication can be identified.

3.2. SASL Passthrough

Use SASL Passthrough (the default) when:

  • You do not need the proxy to know the client’s identity.

  • Your filters do not require an authenticated subject (for example, you are using only record encryption or record validation).

  • You want the simplest possible configuration.

Because the broker still authenticates the client and sees the same identity as if the client had connected without the proxy, broker-side features that depend on client identity — such as authorization (ACLs), audit logging, and quotas — continue to work without any changes to your existing broker configuration.

Be aware that in this mode the proxy cannot log which client is making requests, and identity-aware filters cannot function.

3.3. SASL Passthrough Inspection

Use SASL Passthrough Inspection when:

  • You need the proxy to know the client’s identity (for example, to use the Authorization filter or EntityIsolation filter).

  • You want the broker to remain the authority for authentication decisions.

Because the broker remains the authentication authority and sees the same client identity as if the client had connected without the proxy, broker-side features that depend on client identity — such as authorization (ACLs), audit logging, and quotas — continue to work without any changes to your existing broker configuration.

Consider the following:

  • The broker still decides whether authentication succeeds. An unauthenticated attacker that can reach the proxy still has proxied access to the broker — the proxy forwards their application requests without restriction. If your threat model requires that only authenticated clients' requests are forwarded to the broker, consider OAuthBearer Validation, SASL Termination, or mTLS instead.

  • The proxy observes the SASL exchange and holds the authorization ID in memory. For mechanisms that transmit credentials in plain text (such as PLAIN), this means plain-text passwords briefly exist in the proxy’s memory. The PLAIN mechanism is disabled by default for this reason.

3.4. OAuthBearer Validation

Use OAuthBearer Validation when:

  • Your Kafka clients authenticate using OAuth 2.0 bearer tokens (the OAUTHBEARER SASL mechanism).

  • You want the proxy to reject clients with invalid or expired tokens before their application requests are forwarded to the broker.

  • You want to reduce load on the broker from repeated invalid authentication attempts.

This mode requires a reachable JWKS endpoint that provides the public keys used to verify JWT signatures.

3.5. SASL Termination

Use SASL Termination when:

  • You want the proxy to be the sole authority for client authentication, fully decoupling it from the broker.

  • You need to ensure that only authenticated clients' application requests are forwarded to the broker.

  • Your Kafka clients authenticate using the OAUTHBEARER, SCRAM-SHA-256, or SCRAM-SHA-512 SASL mechanism.

Authenticating clients at the proxy means that every broker feature which depends on client identity needs to be reconsidered:

  • Authorization: The broker sees application requests as coming from the proxy, not from the original client. You can move authorization responsibility to the proxy using the Authorization filter, or you can update your broker’s authorization configuration so that the proxy’s identity is authorized appropriately.

  • Audit logging: Broker-side audit logs record the proxy’s identity, not the original client’s identity. If you need client-level audit trails, you need to rely on proxy-side logging.

  • Quotas: Broker-side quotas apply to the proxy’s identity, not to individual clients. If you need per-client quota enforcement, you need to implement it at the proxy level.

Consider the following:

  • The proxy validates credentials directly and does not forward SASL exchanges to the broker. The broker does not need to be configured for SASL authentication at all, or it can use a different authentication mechanism for other clients.

  • Delegation Token APIs (CreateDelegationToken, RenewDelegationToken, ExpireDelegationToken, DescribeDelegationToken) are not available to clients when SASL is terminated at the proxy, because these APIs depend on a broker-side SASL session.

  • SCRAM credential management APIs (AlterUserScramCredentials, DescribeUserScramCredentials) are not available to clients when SCRAM is terminated at the proxy. SCRAM credentials must be managed using the SCRAM credential tool instead.

  • Unlike SASL Passthrough Inspection, SASL Termination enforces authentication at the proxy: clients that fail authentication are rejected before their application requests are forwarded to the broker.

Infrastructure requirements depend on the mechanism: OAUTHBEARER requires a reachable JWKS endpoint that provides the public keys used to verify JWT signatures; SCRAM-SHA-256 and SCRAM-SHA-512 require a credential store containing SCRAM credentials for your users.

3.6. Combining approaches

mTLS and SASL authentication are not mutually exclusive. You can configure both on the same virtual cluster:

  • The transport subject builder creates an initial authenticated subject from the TLS client certificate.

  • If SASL Passthrough Inspection or OAuthBearer Validation is also configured, the SASL subject builder replaces the subject after successful SASL authentication.

This can be useful when you want transport-level identity as a baseline and application-level identity for fine-grained access control.

4. Choosing a SASL mechanism

When configuring SASL authentication, the choice of mechanism affects the security properties, infrastructure requirements, and operational characteristics of your deployment. This section compares the PLAIN, SCRAM, and OAUTHBEARER mechanisms across several security and operational dimensions to help you make an informed choice.

The choice of SASL mechanism is independent of the choice of authentication approach (Passthrough, Inspection, Termination, or OAuthBearer Validation). However, some authentication approaches constrain the available mechanisms. For information about the mechanisms supported by each authentication approach, see Choosing an authentication approach

This section uses server to refer to whichever component performs SASL authentication — either the Kafka broker or the Kroxylicious proxy, depending on your authentication approach. Where a point applies specifically to Apache Kafka brokers or to the proxy, the more specific term is used.

4.1. Mechanism overview

PLAIN

The client sends a username and password in plain text within the SASL exchange. The security of the credentials depends entirely on the TLS layer protecting the connection. PLAIN is defined in RFC 4616.

SCRAM-SHA-256 and SCRAM-SHA-512

The Salted Challenge Response Authentication Mechanism (SCRAM) authenticates the client using a challenge-response protocol. The client proves knowledge of the password without transmitting it. SCRAM is defined in RFC 5802, with the SHA-256 variant specified in RFC 7677.

OAUTHBEARER

The client presents an OAuth 2.0 bearer token (typically a JWT) obtained from an authorization server. Bearer tokens are typically short-lived, limiting the window of exploitation if a token is intercepted. The server validates the token using public keys retrieved from a JWKS endpoint, without requiring the client to send a password. OAUTHBEARER is defined in RFC 7628.

4.2. Security considerations

4.2.1. Protection against TLS termination and middlebox compromise

Threat: An attacker controls or has access to a TLS-terminating component such as a reverse proxy, API gateway, load balancer, or network monitoring appliance.

PLAIN

The plain-text password is visible to any component that terminates TLS before the authentication server. An attacker with access to such a component can capture credentials directly.

SCRAM

The password is never transmitted, even within the TLS session. The SASL exchange contains only nonces and HMAC proofs, so an attacker with access to a TLS-terminating middlebox cannot extract the password from the SASL messages.

OAUTHBEARER

The bearer token is transmitted within the TLS session, similar to PLAIN. However, bearer tokens are typically short-lived, which limits the window during which a captured token can be replayed. The user’s underlying credentials (such as a username and password used to obtain the token from the authorization server) are not exposed.

4.2.2. Protection against rogue servers and man-in-the-middle attacks

Threat: An attacker impersonates the server or interposes between the client and server, for example, by using a compromised internal CA or a malicious proxy certificate.

PLAIN

No protection at the SASL layer. The client sends the password to whatever server terminates TLS. Correctly configured TLS (with proper certificate validation and trusted CAs) is an adequate mitigation of this risk, because TLS itself verifies the identity of the server before any credentials are sent.

SCRAM (without channel binding)

SCRAM provides mutual authentication: the server must prove possession of the user’s ServerKey before authentication completes. This prevents a rogue server that does not possess the correct ServerKey from completing the SCRAM handshake.

The SCRAM standard defines channel binding variants (such as SCRAM-SHA-256-PLUS) that can detect a TLS-terminating man-in-the-middle. However, Apache Kafka does not support SCRAM channel binding variants. Without channel binding, a man-in-the-middle that proxies the full SCRAM exchange between the genuine client and genuine server is not detected.

OAUTHBEARER

The token is sent to whatever server terminates TLS. The token does not reveal the user’s underlying credentials, and the short lifetime of an individual token limits the impact of a single interception. However, if the rogue server remains undetected, it can capture successive tokens over time and maintain ongoing access.

4.2.3. Cross-service token replay

Threat: An attacker obtains a valid bearer token (for example, from application logs, a compromised service, or a TLS-terminating middlebox) and presents it to a different service to gain unauthorized access.

PLAIN

Not applicable. Passwords are not scoped to a particular service, so a stolen password grants access to any service where the same credentials are accepted.

SCRAM

Not applicable. SCRAM credentials are service-specific by design: the derived keys are computed with a salt chosen by the server, so credentials stolen from one service cannot be replayed against another.

OAUTHBEARER

Bearer tokens can include an aud (audience) claim that identifies the intended recipient. If the server is configured to validate the audience, it rejects tokens that were issued for a different service.

To protect against cross-service replay, configure a unique audience value for your Kafka deployment and ensure that both the authorization server and the server enforce it. Tokens issued without an audience claim, or with an overly broad audience, can be replayed against any service that accepts them.

4.2.4. Protection against credential database theft

Threat: An attacker gains access to the authentication credential store on the server.

PLAIN

The server must be able to verify the plain-text password. In principle, a server could store passwords using a strong hashing algorithm, but Apache Kafka currently stores PLAIN credentials as a plain-text username/password mapping in the broker configuration. An attacker who gains access to the broker configuration obtains all passwords directly.

SCRAM

The server stores derived keys (StoredKey and ServerKey) computed using PBKDF2. An attacker who obtains these derived keys cannot directly authenticate as the client — StoredKey is a one-way hash of ClientKey, so producing a valid authentication proof requires an offline attack to reverse the hash. The attacker can, however, impersonate the server using ServerKey. Crucially, the original password cannot be recovered from the stored keys, which prevents credential-stuffing attacks against other services where the user may have reused the same password.

OAUTHBEARER

The server does not store user passwords. It stores only the public keys (via JWKS) used to verify token signatures. Theft of the JWKS public keys does not allow an attacker to generate valid tokens or recover user credentials. The credential store is maintained by the authorization server, not the server.

4.2.5. Resistance to password recovery from stolen credentials

Threat: An attacker who has stolen the credential store attempts to recover user passwords, either directly or through offline brute-force and dictionary attacks.

PLAIN

None. Apache Kafka currently stores PLAIN credentials in plain text, so an attacker who obtains the credential store has immediate access to all passwords with no cracking required.

SCRAM

Moderate. The SCRAM protocol (RFC 5802 / RFC 7677) mandates PBKDF2 for key derivation, so an attacker must perform an offline brute-force or dictionary attack to recover passwords. However, PBKDF2 lacks memory hardness, which makes GPU-based cracking significantly faster compared to memory-hard algorithms such as Argon2id or bcrypt. The PBKDF2 iteration count can be increased to raise the cost of cracking, but this also increases the cost of legitimate authentication.

OAUTHBEARER

Not applicable. The server does not store passwords; it stores only the public keys used to verify token signatures. Resistance to password recovery depends entirely on the authorization server’s credential storage practices.

4.3. Operational considerations

4.3.1. External identity provider compatibility

PLAIN

Because the server receives the raw password, it can forward the password to any external authentication backend such as LDAP, Active Directory, or PAM. This makes PLAIN the most flexible mechanism for integration with legacy or third-party identity infrastructure.

SCRAM

SCRAM requires the server to store SCRAM-specific derived keys (StoredKey, ServerKey, salt, and iteration count). External identity directories such as LDAP or Active Directory do not natively store SCRAM derivation keys, making integration with these backends difficult.

OAUTHBEARER

Designed for integration with external identity providers. The authorization server handles user authentication and can integrate with LDAP, Active Directory, social identity providers, multi-factor authentication, and other enterprise identity infrastructure. The server only needs to validate the resulting tokens.

4.3.2. Authentication latency

Kafka uses long-lived connections, with authentication at connection establishment and occasional reauthentication. The additional latency from extra authentication round trips is small in this context and is not normally a paramount concern.

PLAIN

Requires one round trip: the client sends credentials, and the server responds with success or failure.

SCRAM

Requires two round trips for the challenge-response exchange (client-first → server-first → client-final → server-final). Over high-latency network links, this doubles the authentication negotiation time compared to PLAIN.

OAUTHBEARER

Requires one round trip between the client and server. However, the client must first obtain a token from the authorization server, which adds latency before the Kafka connection is established. Token caching and refresh strategies can spread this cost across multiple connections.

4.3.3. Infrastructure requirements

PLAIN

No additional infrastructure beyond the server (or whatever backend the server delegates authentication to).

SCRAM

No additional infrastructure beyond the server. Credential management (creating and updating SCRAM credentials) is handled through Kafka’s built-in tooling.

OAUTHBEARER

Requires an OAuth 2.0 authorization server and a JWKS endpoint for token validation. The availability of authentication depends on these services being reachable.

4.3.4. Reauthentication and credential rotation

Kafka supports reauthentication on long-lived connections (KIP-368). When reauthentication is enabled, the broker tells the client when its session expires, and the client initiates a fresh SASL handshake on the existing connection before the session lifetime elapses.

OAUTHBEARER

The session lifetime is derived from the token’s expiry time. When reauthentication occurs, the client obtains a fresh token from the authorization server, so reauthentication also rotates the credential. If an earlier token was compromised, the new handshake uses a different token, limiting the window of exposure.

SCRAM

The Kafka SCRAM implementation does not set a credential lifetime. Reauthentication occurs only if the broker’s connections.max.reauth.ms is configured, and the client re-sends the same password-derived proof. Because the underlying password does not change during reauthentication, credential rotation does not occur. An exception is SCRAM authentication using delegation tokens: the delegation token’s expiry time is used as the credential lifetime, and reauthentication behaves similarly to OAUTHBEARER.

PLAIN

Like SCRAM, no credential lifetime is set. Reauthentication is driven solely by connections.max.reauth.ms, and the client re-sends the same username and password. No credential rotation occurs.

4.3.5. Implementation and parser complexity

PLAIN

Trivially parsed (\0username\0password), minimizing the parser bug surface area.

SCRAM

Requires cryptographic hashing, HMACs, nonce tracking, and a multi-step state machine. The SCRAM standard mandates SASLprep normalization of usernames and passwords, but Apache Kafka does not currently implement SASLprep. Incorrect implementations can introduce timing attacks or normalization bypasses.

OAUTHBEARER

Requires JWT parsing, signature verification against JWKS, and validation of standard claims (expiry, audience, issuer). Client libraries must handle token acquisition and refresh.

4.4. When to use each mechanism

Use PLAIN when

  • You need to integrate with an external identity provider such as LDAP, Active Directory, or PAM, because the server receives the raw password and can forward it to any authentication backend.

  • You want the simplest possible SASL configuration with minimal client and server complexity.

  • You accept that credentials are only protected by the TLS layer and that credential rotation requires out-of-band password changes.

Use SCRAM when

  • You want to protect credentials against TLS-terminating middleboxes or compromised TLS endpoints, because the password is never transmitted.

  • You do not need to integrate with external identity providers that lack SCRAM-specific credential storage.

  • You want protection against credential database theft, where the stored derived keys cannot be directly used to impersonate a client.

Use OAUTHBEARER when

  • You have (or are willing to deploy) an OAuth 2.0 authorization server and JWKS endpoint.

  • You want automatic credential rotation through short-lived tokens, so that compromised credentials expire without manual intervention.

  • You need to integrate with enterprise identity infrastructure such as OpenID Connect, multi-factor authentication, or federated identity.

  • You want reauthentication to rotate the credential, not just re-verify the same one.

5. Understanding subjects and subject builders

When the proxy authenticates a client, it constructs an authenticated subject that represents the client’s identity. This subject is made available to filters in the proxy chain so that they can make decisions based on who the client is.

5.1. Subjects and principals

A subject contains a set of principals. Each principal is a named identifier that represents one aspect of the client’s identity. For example, a principal might represent a user name, an email address, or a group membership.

A subject may contain at most one User principal, which represents the primary identity of the client.

If no authentication is configured, or if authentication has not yet completed, the subject is anonymous — it contains no principals.

5.2. Subject builders

Subject builders are responsible for constructing the authenticated subject from information obtained during authentication. The proxy provides two types of subject builder, corresponding to the two authentication mechanisms:

Transport subject builder

Builds a subject from information in the client’s TLS certificate. The transport subject builder runs after the TLS handshake completes and has access to the client certificate’s distinguished name (DN) and subject alternative names (SANs).

The transport subject builder is configured on the virtual cluster. See Configuring the transport subject builder for configuration details.

SASL subject builder

Builds a subject from information obtained during a successful SASL authentication exchange, such as the SASL authorization ID.

The SASL subject builder is configured on the SASL filter (for example, the SaslInspection filter). See Configuring SASL subject builder for configuration details.

Both subject builders use a pluggable architecture. The default implementations extract principals from certificate fields or SASL authorization IDs using configurable mapping rules. Custom implementations can augment the subject with information looked up from external trusted systems, such as a directory service (for example, ActiveDirectory or LDAP), to add additional principals representing roles or group memberships.

5.3. Subject lifecycle

The authenticated subject evolves through the connection lifecycle:

  1. TLS handshake — If a transport subject builder is configured and the client presents a TLS certificate, the builder creates the initial subject. If no transport subject builder is configured, or if TLS client authentication is not enabled, the subject starts as anonymous.

  2. SASL authentication — If a SASL-aware filter (such as the SaslInspection filter) is configured and the client authenticates successfully via SASL, the SASL subject builder creates a new subject that replaces the transport subject.

  3. Re-authentication — Kafka supports re-authentication (KIP-368). When a client re-authenticates, the SASL subject builder creates a new subject that replaces the previous one.

  4. Authentication failure — If SASL authentication fails, the subject reverts to anonymous.

6. Configuring client mutual TLS (mTLS)

To use mTLS for client authentication, configure TLS on the virtual cluster gateway with a trust store containing the CA certificates that the proxy uses to validate client certificates.

Prerequisites

  • An instance of Kroxylicious. For information on deploying Kroxylicious, see the Kroxylicious Proxy guide or Kroxylicious Operator for Kubernetes guide.

  • A server certificate for the virtual cluster gateway.

  • A trust store containing the CA certificates used to sign client certificates.

  • Client certificates issued by a trusted CA for each Kafka client that needs to authenticate.

6.1. Securing connections from clients

To secure client connections to virtual clusters, configure TLS within the virtual cluster gateway by doing the following:

  • Obtain a server certificate for the virtual cluster from a Certificate Authority (CA).
    Ensure the certificate matches the names of the virtual cluster gateway’s bootstrap and broker addresses.
    This may require wildcard certificates and Subject Alternative Names (SANs).

  • Provide the TLS configuration using the tls properties in the virtual cluster gateway’s configuration to enable it to present the certificate to clients. Depending on your certificate format, apply one of the following examples.

  • For mutual TLS, use the trust properties to configure the virtual cluster gateway to use TLS client authentication.

  • If required, you can restrict the TLS protocols and cipher suites that are used to form the TLS connection.

7. Configuring the transport subject builder

Some filters require the verified identity of the client, derived from successful authentication. This identity is called the authenticated subject.

For applications that use TLS client authentication, the virtual cluster can build the authenticated subject from information in the TLS client certificate presented to the proxy.

The transport subject builder controls how certificate information is turned into principals within the authenticated subject. For example, you can build a principal from parts of the X500 principal. A typical use case is mapping a distinguished name such as CN=myapp,OU=dev,O=kroxylicious.io,C=US to myapp.

For applications that use SASL authentication, see the Client Authentication guide for information on building the authenticated subject from a successful client–broker SASL authentication.

7.1. Configuration

The following example shows configuration for the transport subject builder:

# ...
virtualClusters:
  - name: my-cluster-proxy
    # ...
    subjectBuilder:
      type: DefaultTransportSubjectBuilderService
      config:
        addPrincipals:
          - from: <field name>
            map:
              - replaceMatch: <match replace flags 1>
              - # ...
              - replaceMatch: <match replace flags n>
              - else: identity|anonymous
            principalFactory: <principal factory>
        # - from: ...

where:

  • <field name> identifies the field to extract. Valid field names are listed in the Supported fields table.

  • <match replace flags 1>…​<match replace flags n> define a set of replacement matchers used to match and transform the field value.

  • else defines the behavior when none of the replacement matchers match the field value. identity generates a principal based on the original (unmapped) field value. anonymous generates an anonymous principal.

  • <principal factory> the name of a PrincipalFactory implementation. Currently, only UserFactory is supported.

Field values are tested against the replacement matchers in the order they are configured. The first matcher that matches the field value generates the principal. After a successful match, remaining matchers for that field are ignored.

If no matcher matches, the outcome is defined by the else clause. If there is no match and no else cause is provided, no principal is generated for this field.

Currently, the subject builder is restricted to producing a subject containing at most one user principal.

7.3. Replacement matchers

Replacement matchers control how field values are matched and transformed. A replacement matcher is defined using this format:

/<matching regular expression>/<replacement>/<flags>

where:

  • <matching regular expression> is the regular expression used to test the field value.

  • <replacement> defines the replacement value to use when the regular expression is matched. The replacement can use back references ($1 etc) to refer to capturing groups defined within the regular expression.

  • <flags> (optional) can be either L or U for lower or upper-casing respectively. The case transformation is applied to the replacement value after any back reference resolution.

8. Configuring SASL Passthrough

SASL Passthrough is the default SASL authentication mode. No explicit configuration is required to enable it.

When no SASL-related filter (such as SaslInspection or OauthBearerValidation) is configured in the filter chain, the proxy forwards all SaslHandshake and SaslAuthenticate requests from the client to the broker and relays the broker’s responses back to the client without inspecting or modifying them.

If your Kafka clients and brokers are already configured with SASL authentication, the proxy forwards the SASL exchange transparently. The client authenticates with the broker exactly as it would without the proxy.

In this mode, the authenticated subject remains anonymous. The proxy does not know the client’s identity and cannot make per-client decisions or log identity information. If you need the proxy to be aware of the client’s identity, configure either SASL Passthrough Inspection or OAuthBearer Validation.

10. Configuring SASL Termination

To enable SASL Termination, configure a SaslTermination filter in the proxy’s filter chain. This filter handles the SASL authentication exchange at the proxy without forwarding it to the broker. The proxy validates the client’s credentials directly and constructs an authenticated subject on success.

  • An instance of Kroxylicious. For information on deploying Kroxylicious, see the Kroxylicious Proxy guide or Kroxylicious Operator for Kubernetes guide.

  • For the SCRAM-SHA-256 or SCRAM-SHA-512 mechanism, a credential store containing the SCRAM credentials for your users. The built-in ScramCredentialFileService uses a proxy SCRAM credential file populated using the SCRAM credential tool.

10.1.1. OAUTHBEARER mechanism configuration

The OAUTHBEARER mechanism validates JWT bearer tokens against a JWKS endpoint.

  • jwksEndpointUrl (required) specifies the OAuth/OIDC provider endpoint from which the JSON Web Key Set (JWKS) is retrieved.

  • expectedAudience (required) specifies the expected audience claim value used to verify the JWT. Use a comma-separated list for multiple valid audiences.

  • expectedIssuer (required) specifies the expected issuer claim value used to verify the JWT.

The following properties are optional:

  • scopeClaimName specifies an alternative claim name for the scope in the JWT payload.

  • subClaimName specifies an alternative claim name for the subject in the JWT payload.

  • jwksEndpointRefresh specifies the interval between refreshes of the JWKS cache used to verify JWT signatures.

  • jwksEndpointRetryBackoff specifies the initial delay between attempts to retrieve the JWKS from the external authentication provider.

  • jwksEndpointRetryBackoffMax specifies the maximum delay between JWKS retrieval attempts.

Credential file store configuration

  • file (required) specifies the path to the proxy SCRAM credential file.

    • passwordFile specifies the path to a file containing the password. This is the recommended approach for production deployments.

10.3. Managing SCRAM credentials

Use the SCRAM credential tool to create and manage a proxy SCRAM credential file for SCRAM-SHA-256 and SCRAM-SHA-512 authentication. The tool ships in the Kroxylicious distribution at bin/scram-credential-tool.sh.

The proxy SCRAM credential file stores SCRAM derived keys, not plaintext passwords. By default, the tool prompts you for a password and requires you to confirm it when you set a new password. For more information about the proxy SCRAM credential file format and security properties, see SCRAM security considerations

Prerequisites

  • A Kroxylicious distribution installed on the system where you run the tool.

  • Java 21 or later.

Procedure

  1. Generate a strong file password and save it to a file:

    openssl rand -base64 32 > /etc/kroxylicious/file-password.txt

    You use this password when prompted by the credential tool commands below.

  2. Create a new proxy SCRAM credential file:

    bin/scram-credential-tool.sh create \
  -f /etc/kroxylicious/scram-credentials.p12

    The tool prompts for a file password. Enter the password generated in step 1.

    On POSIX filesystems, the tool automatically restricts file permissions to owner-only access. If you create the file on a non-POSIX filesystem (such as Windows) and later transfer it to a POSIX system, restrict permissions manually:

    chmod 600 /etc/kroxylicious/scram-credentials.p12

  3. Add a user with SCRAM-SHA-256 credentials:

    bin/scram-credential-tool.sh add-user \
  -f /etc/kroxylicious/scram-credentials.p12 \
  -u alice \
  -m SCRAM-SHA-256 \
  -i 10000

    The tool prompts for the file password and the user’s password. Passwords must be at least 12 characters long. There is no restriction on which characters may be used, but sticking to ASCII alphabetic characters, digits, and punctuation is advised.

    -m selects the SCRAM mechanism. Valid values are SCRAM-SHA-256 (default) and SCRAM-SHA-512.

    -i sets the PBKDF2 iteration count (default 10000, minimum 4096). Higher values increase the cost of brute-force attacks against the credential store but also increase the CPU cost of each authentication.

  4. List users in the credential file:

    bin/scram-credential-tool.sh list-users \
  -f /etc/kroxylicious/scram-credentials.p12

    The output shows each user’s name, mechanism, and iteration count.

  5. Update a user’s password:

    bin/scram-credential-tool.sh update-password \
  -f /etc/kroxylicious/scram-credentials.p12 \
  -u alice

    The tool prompts for the file password and the new user password. The -m and -i options are also available if you need to change the mechanism or iteration count.

  6. Remove a user:

    bin/scram-credential-tool.sh remove-user \
  -f /etc/kroxylicious/scram-credentials.p12 \
  -u alice

10.4. SCRAM security considerations

This section describes the security measures that the SaslTermination filter applies when handling SCRAM-SHA-256 and SCRAM-SHA-512 authentication.

10.4.1. Credential storage

The SCRAM credential tool creates a proxy SCRAM credential file — a PKCS#12 file with an internal format specific to Kroxylicious. Always use the SCRAM credential tool to create and modify this file; other tools such as the JDK keytool are not compatible with the internal format.

The proxy SCRAM credential file does not contain plaintext passwords. When a user is added, the password is processed through PBKDF2 key derivation to produce two derived keys: StoredKey and ServerKey. Only these derived keys and the associated salt and iteration count are stored.

The PBKDF2 iteration count controls the computational cost of deriving keys from a password. Higher values increase resistance to brute-force attacks against the credential file, but also increase the CPU cost of each authentication. The default is 10000, and the minimum is 4096.

10.4.2. Username enumeration protection

The filter protects against username enumeration attacks by generating synthetic SCRAM challenges for unknown usernames. These phantom challenges are constructed so that an attacker cannot distinguish between a response for a valid user and a response for a non-existent user.

To maintain this protection, the phantomIterations configuration property should match the iteration count used when creating real credentials. The iteration count is sent as a plaintext field in the SCRAM server challenge message, so if phantom challenges use a different iteration count than real credentials, an attacker can simply compare the values across attempts to distinguish real usernames from non-existent ones.

All proxy instances must use the same proxy SCRAM credential file, because it contains a secret key used to derive phantom salts. If different instances used different files, phantom challenges for the same username would produce different salts across instances, which could reveal which challenges are phantom.

10.4.3. Timing side-channel mitigation

The fixedAuthDelay property (configured at the SaslTermination filter level, not per mechanism) applies a fixed delay to each authentication round. This ensures that authentication responses take a consistent amount of time regardless of whether the user exists, the password is correct, or any other condition. The default delay is 200 milliseconds.

If connection latency is a higher priority than timing attack mitigation, the delay can be set to 0s to disable it entirely. The value can also be tuned to a lower delay, but if it is configured low enough that authentication processing frequently exceeds the fixed delay, the timing attack mitigation is lost. The kroxylicious_filter_sasl_termination_auth_duration_seconds metric records the real authentication latency exclusive of the fixed delay, and the filter logs a warning when authentication processing exceeds it. Use these to inform any tuning. For details, see the Authentication metrics and Authentication logging sections of this guide.

      authenticateCacheMaxSize: 1000
      expectedAudience: https://first.audience, https//second.audience
      expectedIssuer: https://your-domain.auth/

where:

  • jwksEndpointRefreshMs specifies the interval, in milliseconds, between refreshes of the JWKS cache used to verify JWT signatures.

  • jwksEndpointRetryBackoffMs specifies the initial delay, in milliseconds, between attempts to retrieve the JWKS from the external authentication provider.

12. Configuring SASL subject builder

By default, the SASL Inspection filter creates an authenticated subject with a principal that contains the SASL authorized ID. You can change this behavior by providing an alternative subject builder configuration.

12.1. Configuration

The following example shows configuration for the SASL subject builder:

# ...
subjectBuilder: DefaultSaslSubjectBuilderService
subjectBuilderConfig:
    addPrincipals:
      - from: <field name>
        map:
          - replaceMatch: <match replace flags 1>
          - # ...
          - replaceMatch: <match replace flags n>
          - else: identity|anonymous
        principalFactory: <principal factory>

where:

  • <field name> identifies the field to extract. Valid field names are listed in the Supported fields table.

  • <match replace flags 1>…​<match replace flags n> define a set of replacement matchers used to match and transform the field value.

  • else defines the behavior when none of the replacement matchers match the field value. identity generates a principal based on the original (unmapped) field value. anonymous generates an anonymous principal.

  • <principal factory> the name of a PrincipalFactory implementation. Currently, only UserFactory is supported.

Field values are tested against the replacement matchers in the order they are configured. The first matcher that matches the field value generates the principal. After a successful match, remaining matchers for that field are ignored.

If no matcher matches, the outcome is defined by the else clause. If there is no match and no else cause is provided, no principal is generated for this field.

Currently, the subject builder is restricted to producing a subject containing at most one user principal.

12.2. Supported fields

Field name Description

saslAuthorizedId

The SASL authorized ID returned by the SASL authentication exchange.

12.3. Replacement matchers

Replacement matchers control how field values are matched and transformed. A replacement matcher is defined using this format:

/<matching regular expression>/<replacement>/<flags>

where:

  • <matching regular expression> is the regular expression used to test the field value.

  • <replacement> defines the replacement value to use when the regular expression is matched. The replacement can use back references ($1 etc) to refer to capturing groups defined within the regular expression.

  • <flags> (optional) can be either L or U for lower or upper-casing respectively. The case transformation is applied to the replacement value after any back reference resolution.

13. Authentication metrics

When a filter announces a client authentication outcome, the proxy records it as a metric. This allows operators to monitor authentication activity across all virtual clusters and SASL mechanisms.

13.1. Available metrics

Table 5. Authentication metrics
Metric name Type Labels Description

kroxylicious_client_auth_total

Counter

virtual_cluster, mechanism, outcome

Incremented by one every time a filter announces a client authentication outcome. The mechanism label identifies the SASL mechanism used (for example, SCRAM-SHA-256, OAUTHBEARER), or unknown if the mechanism could not be determined. The outcome label is success or failure.
This metric is emitted by the proxy runtime, not by individual filters. It is incremented whenever a filter calls clientSaslAuthenticationSuccess or clientSaslAuthenticationFailure on the filter context. Both the SaslInspection and SaslTermination filters trigger this metric. In SASL Passthrough mode (the default, with no SASL filter configured), no filter announces authentication outcomes, so this metric is not incremented.

13.2. SASL Termination metrics

The SaslTermination filter emits additional metrics specific to the termination process.

Table 6. SASL Termination metrics
Metric name Type Labels Description

kroxylicious_filter_sasl_termination_auth_duration_seconds

Timer

mechanism, virtual_cluster

Records the authentication latency, exclusive of the configured fixed timing delay. This measures the real work performed during authentication: credential store lookup, token validation, and signature verification. Recorded on both successful and failed authentication attempts.

13.3. Operational use

Use kroxylicious_client_auth_total to:

Monitor authentication failure rates

A sudden increase in kroxylicious_client_auth_total{outcome="failure"} may indicate misconfigured clients, expired credentials, or a brute-force attempt.

Example Prometheus alert:

rate(kroxylicious_client_auth_total{outcome="failure"}[5m]) > 10
Compare authentication activity across mechanisms

Break down authentication events by the mechanism label to understand which SASL mechanisms are in use across your deployment.

Detect unexpected mechanisms

Alert if clients authenticate using a mechanism you do not expect, which may indicate a misconfigured client or an attempt to use a weaker mechanism.

Correlate with connection metrics

Compare kroxylicious_client_auth_total{outcome="success"} with kroxylicious_client_to_proxy_connections_total to understand what proportion of connections successfully authenticate.

Tune the fixed authentication delay

Use kroxylicious_filter_sasl_termination_auth_duration_seconds to understand how long authentication actually takes. If the p99 latency approaches or exceeds the configured fixedAuthDelay, the filter logs a warning and the timing side-channel mitigation is less effective. Consider increasing fixedAuthDelay to maintain a margin above the observed authentication latency.

Alert on session expiry

A rising kroxylicious_filter_sasl_termination_session_expired_total indicates that clients are not reauthenticating before their sessions expire. This may indicate misconfigured clients, network issues preventing reauthentication, or a maxTimeBeforeReauth value that is too short for the workload.

For the full list of proxy metrics, see the monitoring section of the Kroxylicious Proxy guide.

14. Authentication logging

The proxy emits structured log messages for authentication events. These log messages provide visibility into authentication activity and can serve as a basic form of audit trail until a dedicated audit log is available.

14.1. Runtime authentication logs

The proxy runtime logs authentication outcomes announced by filters at INFO level. These messages are emitted by the FilterHandler class regardless of which filter triggers the authentication event.

Authentication success

Logged at INFO level with the following structured fields:

  • mechanism — the SASL mechanism used (for example, SCRAM-SHA-256)

  • subject — the authenticated subject constructed by the subject builder

    Message: Filter announces client has passed SASL authentication

Authentication failure

Logged at INFO level with the following structured fields:

  • mechanism — the SASL mechanism used, or null if not yet determined

  • authorizedId — the authorization ID of the client, or null if not available

  • error — the error message from the authentication failure

    Message: Filter announces client has failed SASL authentication

    The full stack trace is included only when the log level is set to DEBUG. At INFO level, the log message includes a hint to increase the log level for the stack trace.

16. Glossary

Glossary of terms used in the Client Authentication guide.

JWE

JSON Web Encryption is an IETF standard for exchanging encrypted data using JSON.

JWKS

JSON Web Key Set is an IETF standard for representing cryptographic keys in JSON format. A JWKS endpoint publishes the public keys used to verify JWT signatures.

JWS

JSON Web Signature is an IETF-proposed standard for signing arbitrary data.

JWT

JSON Web Token is an IETF standard for securely transmitting information between parties as a JSON object.

mTLS

Mutual TLS. A TLS configuration in which both the server and the client present certificates to each other, providing mutual authentication.

Principal

A named identifier that represents one aspect of an authenticated client’s identity, such as a user name or a group membership.

PBKDF2

Password-Based Key Derivation Function 2 is a key derivation function used by SCRAM to derive stored keys from passwords. Defined in RFC 2898.

SASL

Simple Authentication and Security Layer is an IETF framework for handling authentication.

SASL Passthrough

A mode in which the proxy forwards SASL authentication exchanges between client and broker without inspecting or modifying them. This is the default behavior.

SASL Passthrough Inspection

A mode in which the proxy observes SASL authentication exchanges to infer the client’s identity without altering the exchange. The broker remains the authority for authentication decisions.

SASL Termination

A mode in which the proxy handles SASL authentication itself, without forwarding to the broker. The proxy validates credentials directly and constructs an authenticated subject on success.

SCRAM

Salted Challenge Response Authentication Mechanism is a family of SASL mechanisms that authenticate clients using a challenge-response protocol. The password is never transmitted. Defined in RFC 5802.

Subject

The authenticated identity of a client, composed of one or more principals. Used by filters to make identity-aware decisions.

About this guide

This guide covers using the Kroxylicious Protocol Logger Filter. This filter logs the Kafka protocol requests and responses that pass through the proxy as JSON, providing a wire-level protocol trace for debugging and demonstration purposes.

Refer to other Kroxylicious guides for information on running the proxy or for advanced topics such as plugin development.

This filter logs the Kafka protocol requests and responses that pass through the proxy. Every field of every message for the configured API keys is logged as version-aware JSON. This is a wire-level protocol trace, not a curated view of what a client is doing, and it is intended for debugging and demonstration purposes.

The filter is silent by default. For output to appear, the logging backend must be enabled at the filter’s configured log level for the logger used by the filter instance. This means the same filter configuration can be deployed everywhere and operators can turn output on and off from the logging backend, without a proxy restart or configuration change.

1. Configuring the Protocol Logger filter

This procedure describes how to set up the Protocol Logger filter by configuring it in Kroxylicious.

Prerequisites

  • An instance of Kroxylicious. For information on deploying Kroxylicious, see the Kroxylicious Proxy guide or Kroxylicious Operator for Kubernetes guide.

Procedure

  1. Configure a ProtocolLogger type filter.

    • In a standalone proxy deployment. See Example proxy configuration file

    • In a Kubernetes deployment using a KafkaProtocolFilter resource. See Example KafkaProtocolFilter resource

  2. Enable the logging backend at the configured level for the logger used by the filter instance, as described in Enabling log output.

1.1. Example proxy configuration file

If your instance of the Kroxylicious Proxy runs directly on an operating system, provide the filter configuration in the filterDefinitions list of your proxy configuration.

Here is a complete example of a filterDefinitions entry configured for the Protocol Logger:

filterDefinitions:
  - name: my-protocol-logger-filter
    type: ProtocolLogger
    config:
      logLevel: DEBUG
      apiKeyNames:
        - METADATA
        - PRODUCE
        - FETCH
      loggerName: protocol.downstream

where:

  • logLevel (optional) is the SLF4J level at which the filter emits log messages. Defaults to DEBUG. The logging backend must be enabled at this level for the filter’s logger, otherwise no output appears.

  • apiKeyNames (optional) is the set of Kafka ApiKeys enum names to log. If absent or empty, all API keys are logged. Names are resolved case-insensitively and with non-alphanumeric characters stripped, so FindCoordinator, find-coordinator, and FIND_COORDINATOR all resolve to the same API key.

  • loggerName (optional) is the SLF4J logger name used by this filter instance. Defaults to the filter class name, io.kroxylicious.filter.protocollogger.ProtocolLoggerFilter.

All configuration properties are optional, so the config block may be omitted entirely to log all API keys at DEBUG level.

On an idle consumer the output is dominated by HEARTBEAT and FETCH messages. Use apiKeyNames to filter these out. This filter skips decoding for API keys not in the configured set, avoiding formatting cost for excluded messages. Note that another filter in the chain may still require decoding of those same messages.

You can define more than one instance of the filter, placing one at each end of the filter chain to see the effect of the filters between them. Distinct logger names let each instance be enabled independently from the logging backend:

filterDefinitions:
  - name: log-downstream
    type: ProtocolLogger
    config:
      loggerName: protocol.downstream
  - name: log-upstream
    type: ProtocolLogger
    config:
      loggerName: protocol.upstream
defaultFilters:
  - log-downstream
  - some-other-filter
  - log-upstream

Refer to the Kroxylicious Proxy guide for more information about configuring the proxy.

1.2. Example KafkaProtocolFilter resource

If your instance of Kroxylicious runs on Kubernetes, you must use a KafkaProtocolFilter resource to contain the filter configuration.

Here is a complete example of a KafkaProtocolFilter resource configured for the Protocol Logger:

kind: KafkaProtocolFilter
metadata:
  name: my-protocol-logger-filter
spec:
  type: ProtocolLogger
  configTemplate:
    logLevel: DEBUG
    apiKeyNames:
      - METADATA
      - PRODUCE
      - FETCH
    loggerName: protocol.downstream

where:

  • logLevel (optional) is the SLF4J level at which the filter emits log messages. Defaults to DEBUG. The logging backend must be enabled at this level for the filter’s logger, otherwise no output appears.

  • apiKeyNames (optional) is the set of Kafka ApiKeys enum names to log. If absent or empty, all API keys are logged. Names are resolved case-insensitively and with non-alphanumeric characters stripped, so FindCoordinator, find-coordinator, and FIND_COORDINATOR all resolve to the same API key.

  • loggerName (optional) is the SLF4J logger name used by this filter instance. Defaults to the filter class name, io.kroxylicious.filter.protocollogger.ProtocolLoggerFilter.

All configuration properties are optional, so the configTemplate block may be omitted entirely to log all API keys at DEBUG level.

You can define more than one instance of the filter, placing one at each end of the filter chain to see the effect of the filters between them. Distinct logger names let each instance be enabled independently from the logging backend:

kind: KafkaProtocolFilter
metadata:
  name: log-downstream
spec:
  type: ProtocolLogger
  configTemplate:
    loggerName: protocol.downstream
kind: KafkaProtocolFilter
metadata:
  name: log-upstream
spec:
  type: ProtocolLogger
  configTemplate:
    loggerName: protocol.upstream

Reference both resources from the virtual cluster’s filter list, with the other filters between them.

Refer to the Kroxylicious Operator for Kubernetes guide for more information about configuration on Kubernetes.

2. Enabling log output

The filter is silent by default. Two settings must agree for output to appear:

  1. The filter’s own logLevel configuration property (default DEBUG).

  2. The logging backend must be enabled at that level for the logger used by the filter instance.

Setting one without the other produces no output at all. With default settings, adding the filter to your proxy configuration and seeing nothing is expected — the logging backend must also be told to emit DEBUG messages for the filter’s logger.

The simplest way to see output is to set the environment variable before starting the proxy:

KROXYLICIOUS_APP_LOG_LEVEL=DEBUG bin/kroxylicious-start.sh --config proxy-config.yaml

This enables DEBUG for all io.kroxylicious loggers. For a more targeted approach, add a logger entry to log4j2.yaml as described in the next section.

2.1. Runtime log level tuning

The same filter configuration can be deployed to development and production environments. Operators turn output on and off by tuning the logging backend — no proxy restart and no configuration change are required.

Add monitorInterval to the top of your log4j2.yaml so that Log4j 2 re-reads the file periodically. Then add a logger entry for the filter:

Configuration:
  monitorInterval: 5          # re-read this file every 5 seconds
  # ... appenders unchanged ...
  Loggers:
    # ... other loggers ...
    Logger:
      - name: io.kroxylicious.filter.protocollogger.ProtocolLoggerFilter
        level: DEBUG           # change to WARN or OFF to silence
        additivity: false
        AppenderRef:
          - ref: STDOUT

monitorInterval is what makes this work without a restart. Edit the file, change the level, and within monitorInterval seconds the proxy starts or stops emitting protocol traces.

The default log4j2.yaml shipped with the proxy distribution does not include monitorInterval. An operator must add it to enable live tuning.

When using a custom loggerName, the logger entry must match that name instead of the filter class name.

Other SLF4J backends work too — the only requirement is a logger enabled at the configured level for the name used by the filter instance. Log4j 2 is the example because it is what the proxy distribution uses by default.

3. Output format

Each log entry is a single JSON object with a header and a payload. The payload is rendered using Apache Kafka’s generated JSON converters, so the structure follows the exact wire format of the negotiated API version.

An example request entry:

{
  "header" : {
    "type" : "REQUEST",
    "apiKey" : "METADATA",
    "apiVersion" : 13,
    "correlationId" : 1,
    "clientId" : "producer-1"
  },
  "payload" : {
    "topics" : [ {
      "topicId" : "AAAAAAAAAAAAAAAAAAAAAA",
      "name" : "my-topic"
    } ],
    "allowAutoTopicCreation" : true,
    "includeTopicAuthorizedOperations" : false
  }
}

An example response entry:

{
  "header" : {
    "type" : "RESPONSE",
    "apiKey" : "METADATA",
    "apiVersion" : 13,
    "correlationId" : 1
  },
  "payload" : {
    "throttleTimeMs" : 0,
    "brokers" : [ {
      "nodeId" : 1,
      "host" : "localhost",
      "port" : 9194,
      "rack" : null
    } ],
    "clusterId" : "MkU3OEVBNTcwNTJENDM2Qk",
    "controllerId" : 1,
    "topics" : [ ],
    "errorCode" : 0
  }
}

Note that clientId appears only on requests — it does not exist on the wire for responses, and responses omit the key entirely rather than emitting null.

Structured key-values are appended by the logging framework after the JSON body. These include apiKey, apiVersion, clientCorrelationId, direction, and sessionId, plus clientId on requests only.

3.1. Machine-parseable output

Each log entry is JSON, but a log line is not — the logging backend’s timestamp, level, and logger name prefix surround it. Piping raw log output to jq fails unless you either strip the prefix or use a message-only appender.

To get machine-parseable output, add a message-only appender to your log4j2.yaml:

Configuration:
  Appenders:
    Console:
      - name: PROTOCOL_TRACE
        PatternLayout:
          pattern: "%m%n"
  Loggers:
    Logger:
      - name: io.kroxylicious.filter.protocollogger.ProtocolLoggerFilter # or your configured loggerName
        level: DEBUG
        additivity: false
        AppenderRef:
          - ref: PROTOCOL_TRACE

With that appender, each entry is a multi-line pretty-printed JSON object — jq reads the stream directly, but line-oriented tools such as grep do not see one entry per line:

# select METADATA entries (both request and response)
jq -c 'select(.header.apiKey == "METADATA")' < proxy-trace.log

3.2. Pairing requests and responses

Use the sessionId structured key-value together with .header.correlationId. Correlation IDs are only unique within a single connection, so sessionId is required to pair correctly across concurrent connections.

sessionId is deliberately not in the JSON entry — it is proxy-internal state, not part of the protocol trace. It appears only in the structured key-values.

Correlation IDs in the output are not necessarily client correlation IDs. Filters can dispatch out-of-band requests upstream, which carry synthetic negative correlation IDs. Depending on its position in the filter chain, this filter may observe such requests and cannot reliably tell them apart from client traffic, so pairing may produce entries with no counterpart.

Latency can be derived from the log timestamps of matched request and response pairs.

4. Security considerations

The bodies of credential-bearing API keys are never logged. The following API keys are hardcoded as excluded:

  • SASL_AUTHENTICATE

  • CREATE_DELEGATION_TOKEN

  • RENEW_DELEGATION_TOKEN

  • EXPIRE_DELEGATION_TOKEN

  • ALTER_USER_SCRAM_CREDENTIALS

  • DESCRIBE_DELEGATION_TOKEN

This is deliberately not configurable. For these API keys, the message body is structurally withheld rather than redacted after the fact. The header is still emitted so the handshake remains visible; the payload is replaced with a null and a payloadWithheld field explains why:

{
  "header" : {
    "type" : "REQUEST",
    "apiKey" : "SASL_AUTHENTICATE",
    "apiVersion" : 2,
    "correlationId" : 2147483642,
    "clientId" : "producer-1"
  },
  "payload" : null,
  "payloadWithheld" : "credential-bearing API"
}

Record payloads (the content of Produce and Fetch messages) are not logged in readable form. Kafka’s generated JSON converters emit an empty byte array for records-typed fields regardless of content, so the binary record payload never appears in the output.

Other protocol fields are logged verbatim. Metadata such as topic names, consumer group names, and client identifiers may themselves be sensitive in your environment, so treat the resulting log output with the same care as any other log data.
